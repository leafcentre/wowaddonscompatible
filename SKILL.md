# WoW addon version compatibility fixes

Scope: adapting an existing (usually un-maintained) WoW addon so it loads and runs on the current retail patch (12.x Midnight-era). Also covers user requests framed as "ZPerl/TPerl/XYZ doesn't work on 12.x".

## Hard rules

- Port the addon the user names, from its canonical source. If a renamed fork is installed locally, do NOT copy from it or use it as the working base — user explicitly rejects fork-derived work ("我要Zperl" means the original project). Reading a fork locally for orientation is fine only if the user has not forbade it.
- Every TOC file gets `## Interface: <current patch int>` (12.1.0 = `120100`). Since 12.0 mainline addons with a lower interface version are refused outright — no client-side override exists. Setting only the main addon's TOC and forgetting the sub-module TOCs is the classic miss; enumerate all `*.toc`.
- Write compat shims as `if not _G.FuncName then ... end`. Only define what is missing so classic-era clients and older hosts keep native behavior.
- The shim file must load FIRST in the main addon's TOC (before any file that does `local GetSpellInfo = GetSpellInfo`-style upvalue capture at load). Child addons use RequiredDeps so they load after the core; their captures pick the shim up automatically.
- Verify statically, never claim runtime-verified. Report what was checked (syntax, TOC audit) and hand the user `/console scriptErrors 1` for live testing.
- Before judging an edit — as working OR as failed — confirm the running client actually loaded the edited files. SavedVariables are written at session boundaries, not when the files change, so file mtimes prove nothing about what is in memory; the client's own session boundaries are in `_retail_/Logs/General.log`. Do not tell the user "reload and it should be fixed" twice because the first reload was measured wrong. See `references/live-client-measurement.md`.

## Secret-values work (12.0/12.1)

- Triage with `npx wow-secret-lint@1.7.0 <addon dirs> --patch=auto --format=json` (Node 20+). It reads the .toc, follows XML includes, and reports `WSL001/002` (arithmetic/comparison on possibly-secret values), `WSL008` (CLEU registration), `WSL012/018` (aura vectors/`GetAuraDataByIndex`), `WSL013` (unit-identity APIs), `WSL014` (removed symbols, names the replacement). Run it before and after; the error count is the progress metric.
  - It only recognises the literal inline `issecretvalue(v)` guard. Wrapper guards (`XPerl_IsSecretValue(v)`) leave the finding in place even though the runtime path is safe — don't chase those.
  - Findings' line numbers are reliable, but the variable named in the message can be a generic placeholder.
  - Report shape: `{"findings": [...], "parseErrors": [...], "warnings": [...], "summary": {...}}` — there is no top-level `errors` key; each finding carries its own `severity`. When piping the JSON through a parser on Windows, redirect to a `$HOME` file (`> "$HOME/lint.json"`) and read it from the native path — npx stdout redirected to `/tmp`-style or `/c/...` MSYS paths can silently produce nothing.
- Central fix pattern that covers a whole addon: one compat helper that pushes possibly-secret numbers onto the bar under `pcall` and returns "was secret", plus `XPerl_SecretBarTextHide(bar)`; every per-unit update function does `local hp, hpMax, secret = SafeHealth(unit)` and `if secret then feed-bar; hide-text; return end` before any maths. Fixing the shared bar function (`XPerl_SetHealthBar`) covers player/target/party/pet/targettarget at once — and the flip side of that concentration is that its early return is the single point that can suppress every frame's decoration (next bullet).
- **That same `return` suppresses the cosmetics — put the number-INDEPENDENT ones in front of it.** `if secret then feed-bar; hide-text; return end` as the first thing the shared setter does means every decoration that does not actually need the numbers never runs: on 12.x `UnitHealth("player")` can be a Secret Value, so the class colour and the percent text silently fall away while a sibling path with no health dependency (the name, coloured from `UnitClass`) stays correct. Split the number-independent work into its own helper (`ApplyClassColour(self, bar, partyid)`) and call it as the first line of the shared setter so it covers every frame routed through it, keep the arithmetic behind the bail-out, and still nil-guard what remains — `bar:SetMinMaxValues(0, nil)` errors and the error is swallowed by whatever `pcall` wraps the update, leaving the bar looking frozen (use `Max == nil`, not `not Max`: `0` is truthy in Lua and `Max == 0` is a legitimate case the code handles), and a missing percentage must not reach the gradient helper (`if (healthPct) then`, since `smoothColor(nil)` compares nil). Diagnostic signature of this whole class: **the name is class-coloured but the bar is not** — meaning the bar-colour call never ran at all.
- Guard helper family that makes an addon-wide sweep mechanical: `XPerl_Unit_ClassToken(unit)` (cached `select(2, UnitClass(unit))` for class colours / exception tables), `XPerl_Unit_Role(unit)`, `XPerl_Unit_GUID(unit)` (nil when unreadable), `XPerl_SafeBool(value, fallback)`, `XPerl_SafeString(value, fallback)` and `XPerl_SafeValue(fn, fallback)` (pcall-evaluates a whole expression of identity calls). Each returns the real value when readable, so wrapping call sites is behaviour-preserving except in the restricted window. `false` is the right boolean fallback for "show this little icon" decisions.
- `UnitGUID` also returns a **secret string** for restricted units even though `wow-secret-lint` does not flag it (it has no UnitGUID rule). It shows up as `attempt to compare field 'guid' (a secret string value)` from a live BugSack paste. Any comparison, table key (`list[guid]`), `strfind(guid, "-")` or cache lookup on it errors — read it through a nil-returning helper and make "did it change" tests force the update when nil (`if not guid or guid ~= self.guid then`). Consumers that already `if (not guid) then return end` (e.g. highlight tables, `xpHigh:Add`) then degrade cleanly.
- Do not cache unit *names* by unit token the way you cache class: the token's meaning changes with the target, so a stale cache shows the previous target's name. `FontString:SetText(secretName)` does work (no error in live logs), so names only need guarding inside comparisons (`x ~= UNKNOWN`, `~= ""` on the realm return).
- Unit-identity APIs (`UnitClass`, `UnitGroupRolesAssigned`, `UnitIsCharmed`, `UnitIsPVP`, `UnitIsGroupLeader/Assistant`, …) return secrets while a unit's identity is restricted — i.e. for anything outside player/party/raid (targets/targettarget in dungeons, M+, PvP). Party/player hits are harmless; target-side ones are the real ones. Cache the token from an untainted read (out of combat / open world) and fall back to the cache.
- Whole-feature gating beats per-site guarding where a gate exists: BetterBlizzFrames (retail) asks `C_Secrets.ShouldUnitIdentityBeSecret(unit)` before identity-touching work and `C_Secrets.GetSpellAuraSecrecy(spellID) == Enum.SecrecyLevel.NeverSecret` to classify auras — when restricted, the feature skips cleanly instead of running and erroring. Use these for gates; reserve issecretvalue wrappers for values that arrive with no gate.
- Gate 12.x-only skips with a FLAG defined in the compat shim and checked at the call site in the child addon — never a function-level stub in the shim itself: the child addon's own files load after the shim and re-define their functions, silently overwriting the stub.

- **A missing default config key is a silent feature-off, not a secret-value bug.** The port's own `*_Global_ConfigDefault` can omit keys the runtime gates on: Z-Perl's default `colour` table has no `classbar`/`classbarBright`, while `XPerl_ColourHealthBar` gates the whole class-colour branch on `conf.colour.classbar` — so every config rebuild (which happens whenever `QuickValidate` fails) resets the setting, the health bars drop to the smooth/gradient fallback, the in-game checkbox comes up unchecked, and nothing errors. Before blaming the secret layer for "colour/feature X doesn't work", diff the KEYS the code reads against the keys the default table writes: regex `conf\.<section>\.([A-Za-z_]+)` over the addon vs `^\t\t([A-Za-z_]+)\s*=` inside the `default.<section> = {` block, and compare the sets. A key read but never written is a guaranteed no-op; mirror the fix into the compat fallback table too so both paths agree. Trigger this check whenever the user's complaint is cosmetic and the code path looks correct.
- **The addon's OWN secret-value bail-out silently skips every later cosmetic.** Typical port shape: `function SetHealthBar(...) if SecretBarValues(bar, hp, max) then feed-bar; hide-text; return end ... ColourHealthBar(...) end`. On 12.x the health numbers are secret even for the PLAYER (`UnitHealth("player")` — verified on a live 12.1 client), so that `return` fires on every update and the colour call is never reached: health bars sit at their template colour forever. Tell-tale symptom: **names coloured correctly (name colour has no health dependency) while the bars are wrong**. Fix: split the number-independent work out (e.g. `ApplyClassColour(self, bar)`) and call it BEFORE the bail-out in every health update entry point, not just the main one — the target module reuses its own `if isSecret then bar:SetValue(...) else SetHealthBar(...) end` and the target-target frame reuses the target's update function, so one entry point can hide several frames. `healthPct` may then be nil downstream: guard `if healthPct then smooth-colour end`, never feed nil into the gradient maths.
- **A bail-out that sits between "create the frame" and "decide its visibility" leaves a stray frame on screen.** Z-Perl's extra power bar is created by `MakeDruidBar()` and then shown/hidden by a class/spec/form test (`SHAMAN and GetSpecialization()==1 and GetShapeshiftForm()==0`, `DRUID/PRIEST and UnitPowerType(unit)>0`); the secret bail-out returns between the two, so the freshly created bar stays visible as an unexplained extra bar. Compute the visibility decision BEFORE the bail-out (it never depends on the numbers) and re-run the layout call inside the bail-out too.
- **Inverse-fill bars cannot be honoured while the numbers are secret.** The flipped mode is `bar:SetValue(max - value)`, which is arithmetic on a secret and therefore an immediate error. Fill in the normal direction inside the secret branch (`SetValue(value)`, `SetMinMaxValues(0, max)`) and state the trade-off in a comment: the length is right, only the direction is not mirrored for restricted units. Do not "fix" it by reading the value back off the widget (`StatusBar:GetValue()` returns a secret once the bar has been given one).
- **Geometry-affecting side effects belong in front of the secret bail-out too, not just the cosmetics.** `if (secret) then SetManaBarType(); if (not manaBar:IsShown()) then manaBar:Show() end; return end` shows a bar nobody made room for: the frame stays at its old height and the stack is never re-laid-out, so the new bar hangs outside/gaps appear. Mirror the readable branch exactly (`SetHeight(40)` + `StatsFrameSetup(self)`, same frame-list guard) inside the secret branch whenever it changes a bar's visibility.
- **Never interpolate a secret value into a debug string you intend to persist.** `format("...[%s]", UnitHealth("player"))` produces a secret string, and the client serialises the whole saved entry as `nil --[[ secret value ]]` — the payload is lost, but that serialisation is itself a free oracle proving the value is secret. Record only `issecretvalue(v)` / `canaccessvalue(v)` flags. Related: `/reload` writes SavedVariables BEFORE reloading, so a probe recorded in the session you just entered only lands on disk at the NEXT save (reload twice, or log out and back in).
- Diagnosing secret-related symptom reports:
- A cluster of "unrelated" complaints — class colours wrong + bar shows dead/grey while alive + health/mana text frozen + buff and debuff icons missing — is usually ONE cause: the secret-values restriction context is active and every guarded path is silently taking its fallback. Do not debug them as separate bugs; first establish WHERE the user saw it. Restricted contexts (combat, dungeons/raids, M+, PvP) making everything degrade is the expected platform limit; the same symptoms in open world on the player frame or a friendly target means a real bug — have the user run `/dump issecretvalue(UnitHealth("player"))` and `/dump issecretvalue(UnitClass("target"))` to split the cases.
- "No errors but colours missing" means the failure is upstream of the lookup: the class token is nil because UnitClass/UnitIsPlayer came back as secrets, so the colour code never runs. Before hardening colour lookup tables with extra fallbacks (C_ClassColor etc.), confirm a class token is actually arriving — hardening the tail of a chain whose head is nil changes nothing.
- An unexpected, duplicate-looking or oddly-decorated unit frame in a user's screenshot is usually Blizzard's OWN frame that was never replaced: the code that disables it lives in the ADDON MODULE for that unit type, so a module that never loaded (newly added dir, disabled in AddOns.txt, needs a client restart) leaves Blizzard's version alive — complete with its empty black status-icon slots, which read as a drawing bug/dots rather than as "the wrong frame owner". Confirm the ownership before touching any texture or layout code (an addon-side missing texture is a different fault): the module's per-character SavedVariables file is absent, and an automated check of every `file="..."` reference under `Interface\AddOns\<Module>\` comes back clean. `/fstack` + hovering the element is the cheapest in-game way to name whatever frame the user points at.
- Cheap triage before blaming code: read `WTF/Account/<acct>/<realm>/<char>/AddOns.txt` FIRST — one grep for the addon name answers "is the addon even set to load?", and a `disabled` line there sent from the addon's own load path is the whole bug. Each character has its own AddOns.txt; rewrite the name to `enabled` in all of them (they are plain `Name: enabled|disabled` lines) while the game is closed.
- BugGrabber entries carry a `session` (increments per client run) and a `time` (epoch) field: sort by them to separate the CURRENT client run's errors from stale ones whose file paths no longer exist (post-rename leftovers referencing deleted dirs). Fixing "errors" from an old session is wasted work.
- `UnregisterEvent("COMBAT_LOG_EVENT_UNFILTERED")` is a PROTECTED action on 12.x exactly like registering it — the client raises ADDON_ACTION_FORBIDDEN (`插件 'X' 尝试调用保护功能 'X:UnregisterEvent()'`) and `pcall` cannot suppress it. Gate BOTH the register and the unregister branch on the build check, not just the register.
- **`issecretvalue` is only HALF the test — an unreadable value can also be merely inaccessible.** 12.x has two notions: a Secret Value (`issecretvalue(v)`) and a value you simply cannot read in the current restricted context (`canaccessvalue(v) == false`, the test Blizzard's UI and the 12.x-ready addons in the install use — Grid2 ships `canaccessvalue` into a dozen files and its `API.UnitClassSafe` is exactly this pattern). A port that tests only `issecretvalue` passes inaccessible values through untouched, so every boolean gate on one silently takes its fallback with no error to chase. Symptom: "the frame keeps the wrong colour / the feature is off, and BugGrabber is empty". Fix in ONE place: the addon's single secret predicate should return true for either test. Keep `nil` out of it (`v ~= nil and not canaccessvalue(v)`) — callers depend on nil-for-no-unit semantics (`UnitExists`, `UnitName`, `UnitGUID`) and flipping nil to the fallback makes frames for nonexistent units show up.
- When a cosmetic fails while a sibling path using the SAME lookup succeeds, split the chain before editing anything: is the INPUT unreadable (class token nil), or is a boolean GATE discarding a good input? Gate-free paths staying correct (name text coloured by class) while a gated one falls back (health bar behind `RawUnitIsPlayer(unit) == true`) proves the input is fine — `UnitIsPlayer` and friends carry the `AllowedWhenUntainted` predicate, so they can answer with a value that cannot be compared against `true`. Having narrowed it to "a gate", do NOT guess which input is wrong and start editing: instrument the path and read the values it actually resolved to (`references/live-client-measurement.md`). Skipping the gate for a frame whose unit is fixed by definition (`"player"`/`"vehicle"` — the frame IS the player) is sound in principle, but until a probe shows the bar truly took the class colour it is a hypothesis, not a fix.
- When the login snapshot comes back showing every input ALREADY correct (`UnitIsPlayer(player)=[true]` unsecret and accessible, class token readable, gate value truthy, colour table present) and the decision probe still never shows up in the save, stop hardening inputs: the branch is unreachable, and the early return upstream is the bug. Do not ship speculative helper/gate rewrites in the meantime — they are unvalidated behaviour changes layered on top of the real fault, and they make the next measurement harder to read.
- Reading evidence off the disk beats guessing when there is no live client: (1) the saved config often proves a code path RAN — e.g. Z-Perl's `rangeFinder.spell` is only filled by `StartupSpellRange` looking up `DefaultRangeSpells[playerClass]`, so a filled spell (Healing Surge ⇒ SHAMAN) proves `UnitClass` was readable; (2) the name-text colour then separates "token readable" (class colour, e.g. `#0070DD` shaman blue) from "token nil" (the `GetClassColour(nil)` default `{0.5,0.5,1}` = `#8080FF`); (3) sample the bar PIXELS and check the non-green channels — every class colour has a non-zero R or B, so a bar of pure `(0,G,0)` is the `healthFull`/`smoothColor` fallback, never a class colour. Do the sampling with PIL rather than trusting a vision model: on a 2560×1440 UI screenshot the model reported wrong colours twice and wrong regions once.
- When the evidence is not on disk yet, MAKE it land there instead of iterating on hypotheses: have the addon itself write a one-shot snapshot into its SavedVariables (login-time dump at the end of the addon's init, `pcall`-wrapped because `tostring()` on an inaccessible value may itself refuse) rather than asking the user to describe or screenshot the result. Mind the reload timing: a `/reload` writes the saved variables from the session that is ENDING, before the new files load, so a probe added in this round shows up only after a SECOND reload (or a reload plus a log-out). And make the probe REWRITE itself every session (`Config.probeX = nil` in the init handler) if it guards with `if (probe[key] == nil) then` — SavedVariables entries persist, so a write-once probe freezes the values from the FIRST session it ever ran and every later read is stale data mistaken for fresh. Mechanics and the full probe catalogue: `references/live-client-measurement.md`.
- **NPCs have class tokens too, so "a class token came back" does NOT mean "player character".** `UnitClass` on a mob returns the CREATURE's class (`WARRIOR` for a plain humanoid), which Z-Perl feeds straight into its class-colour branch; combined with a sentinel-tolerant gate (`UnitIsPlayer(unit)` unreadable + `class ~= nil` -> colour it) every mob gets a meaningless class colour. **Do NOT use `UnitCreatureType` to tell them apart** — player characters report `Humanoid` (CreatureType ID 7, and `Humanoid` is a normal value for mobs too), so a creature-type test vetoes the player's own class colour and strips it (live regression). Correct rule: a readable `UnitIsPlayer == true` earns the class colour, a readable `false` never does, and when the read is unreadable trust only a unit token previously VERIFIED as a player character (cached with its GUID so a switched target cannot inherit the flag). When in doubt do not colour — a mob in a meaningless class colour looks worse than a plain bar.
- **Turning a bar's class colour OFF requires actively recolouring it.** Once a unit token stops qualifying (target switched from a player to a mob, or the token no longer exists), the bar keeps the previous occupant's class colour forever, because the class-colour function only ever sets a colour and the gradient path is only reached when a percentage exists. Reset to the gradient in the same branches that decide against the class colour. With the raw numbers secret there is no percentage to compute — Blizzard ships `UnitHealthPercent(unit [, usePredicted [, curve]])` (12.0+) for exactly this, returning a displayable 0..1 fraction (`CurveConstants.ScaleTo100` is the 0..100 variant); it is itself marked SecretReturns, so guard it and fall back to the full-health colour when even that is unreadable.
- **Secret values CAN be displayed — never compute, hand them to the widget.** This is the whole design of the 12.x Secret Values system and the trap that costs the most rounds: `FontString:SetFormattedText` / `SetText` are among the APIs that explicitly ACCEPT secret arguments (they apply the "Text" secret aspect, whose only consequence is that reading it back with `GetText()` returns a secret). `string.format` / `concat` / `join` are likewise allowed with secrets. So the health text is `bar.text:SetFormattedText("%s/%s", UnitHealth(unit), UnitHealthMax(unit))` — the EXACT numbers, no derivation. Forbidden on secrets (each is an immediate Lua error): arithmetic, `==` comparisons, `#`, table keys, indexing, calling them as functions, and boolean tests on *boolean* secrets (non-boolean secrets are always truthy, so `if (value)` is legal and is the safe existence test — test `issecretvalue(v)` first, since `v == nil` is itself a forbidden comparison). Percentages need a curve because multiplying a secret by 100 is arithmetic: build one with `C_CurveUtil.CreateCurve()` + `SetType(Enum.LuaCurveType.Linear)` + `AddPoint(0,0)` + `AddPoint(1,100)` (or `CurveConstants.ScaleTo100` when present) and pass it to `UnitHealthPercent(unit, true, curve)` / `UnitPowerPercent(unit, powerType, nil, curve)`, then hand the result straight to `SetFormattedText("%.0f%%", secretPct)`. Bars and gradients have the same escape hatch: `StatusBar:SetValue(secret)` and `C_CurveUtil.CreateColorCurve()` + `Evaluate(secretPct)`.
- **Never `tostring` a secret, not even in a diagnostic string.** The taint propagates into the produced string and the client serialises the whole saved entry as `nil --[[ secret value ]]`, destroying the probe you built (and costing reloads). Classify instead: `issecretvalue(v)` -> "SECRET", `canaccessvalue(v)` -> "NOREAD", then truthiness, then `tostring` only on a readable value. Order matters: test secrecy before any `if (v == nil)`. Both `UnitHealthPercent(unit [, usePredicted [, curve]])` and `UnitPowerPercent(unit, powerType, unmodified, curve)` are annotated `SecretWhenCurveSecret`: the result is secret **iff the curve you hand it is**. Called with no curve / nil it returns a Secret Value (verified by probe on 12.1), which looks exactly like "the API isn't available". Pass an engine-built constant — `CurveConstants.ScaleTo100` (0..100), `CurveConstants.ZeroToOne` (0..1), `Reverse`, `ReverseTo100` — or one you build with `C_CurveUtil.CreateCurve()` + `SetType(Enum.LuaCurveType.Linear)` + `AddPoint`. This is what the still-working 12.x addons do (TargetPercent, IceHUD). Note `UnitPowerPercent` takes the curve as the **4th** argument. Then the percentage is a plain number (or still a secret — hand it straight to `SetFormattedText("%.0f%%", pct)`) and `UnitHealthMax` is readable anyway. Do NOT derive the absolute value as `percent * readable max`: the raw `UnitHealth(unit)` can go straight into `SetFormattedText("%s/%s", hp, max)` for the EXACT number, which is both simpler and accurate. Without this the old code hid both texts wholesale, and one caller did `bar.percent:Show()` on a string it never set, showing a stale/empty percentage.
- **For secret bars, prefer the engine's scaling objects over hand-rolled math.** `StatusBar:SetValue(secretValue)` accepts secrets directly, and `C_CurveUtil.CreateColorCurve()` + `colorCurve:Evaluate(secretPercent)` returns a usable colour for the green->red health gradient, so a bar whose health is secret can still be coloured correctly instead of being forced to one flat colour. Same for `CurveObject:Evaluate`.
- **In a Lua file, a helper defined BEFORE a `local X = Y` alias further down the file cannot see that local** — name resolution happens at compile time, so the reference compiles as a global lookup and blows up at runtime with "attempt to call a nil value (global 'X')" the first time the helper runs. This bites when you insert a new helper above an existing local alias (`local SetValuedText = QueFrame_SetValuedText`); call the global (`QueFrame_SetValuedText`) instead. Same trap for file-scope locals like `local floor = math.floor` — those must already be visible at the insertion point.
- **`local X = X` aliases silently capture REMOVED APIs as nil, and the call then aborts the rest of the function.** Old addons hoist globals into file-scope locals at load; an API the current client no longer has (e.g. `SetPortraitToTexture` gone in 12.x) makes that local nil, so the call site throws `attempt to call a nil value` and **every statement after it in that function never runs** — a whole update/layout path dies with one BugGrabber entry that looks unrelated to the feature the user reports broken. Read the BugGrabber stack (it names the function and the frame), then give each removed alias a fallback (`local Foo = Foo or function(...) ... end`). Sweep for the whole class at once: list every pure alias in the addon (`^local (\w+) = \1$`) and probe `_G[name] == nil` for the list at login, so one reload reports all of them instead of one crash per discovery. Supposed-removed suspects: `SetPortraitToTexture`, `GetTalentInfo`, `GetNumTalents`, `GetPetHappiness`, `GetPVPTimer`, `GetComboPoints`, `UnitPlayerOrPetInParty`.
- **Diagnose display problems from the widget state, not from a screenshot — but classify the state, never read the text back.** Poll each bar's `IsShown()` / `GetWidth()` a few seconds after login (`C_Timer.After`) and prove the fill happened with `FontString:HasSecretAspect(Enum.SecretAspect.Text)`: once a fontstring has been handed a secret it carries the Text aspect, and its `GetText()` THROWS (`invalid value (secret) at index 1 in table for 'concat'`) the moment it reaches a probe string. That throw is the positive proof the value reached the widget, so it is the signal, not a failure — never `tostring` what you read back. This separates "filled from a secret and displaying" from "set but hidden" from "never set at all" in one reload, which a screenshot cannot do.
- **Newly added or renamed addon DIRECTORIES are only scanned at client start — `/reload` will not find them.** After dropping/renaming module folders into `Interface/AddOns`, the user must leave to the character-select screen and re-enter (or restart the client) before the module loads; until then it is silently absent, BugGrabber shows nothing (no errors from a module that never loaded), and any per-module SavedVariables it would write never appear. Do not diagnose "the module errored" from a silent BugGrabber — first check for the module's own SavedVariables file (a `## SavedVariablesPerCharacter:` entry names it) as positive proof it loaded. Also: the per-character `AddOns.txt` entry is the load switch, but editing it for characters where the module was previously absent only matters after that re-entry.
- **Mystery UI element? Have the user run `/fstack` and hover it — do not forensically dissect a screenshot.** The frame-stack tooltip lists the frame name chain and a `SOURCE` line naming the file that created it (`Interface/AddOns/Blizzard_UnitFrame/...` vs your addon), which identifies the owner in one step. Screenshot/pixel analysis and vision-model reads are unreliable at this (they mis-read colours, counts and owner repeatedly) and cost rounds; a frame name plus source file ends the question immediately. This is how a row of unexplained black dots turned out to be `ComboPoint1..5` of Blizzard's `ComboFrame`.
- **An addon that reparents Blizzard's `ComboFrame` can leave it visible on classes with no combo points.** X-Perl/Z-Perl reparents `ComboFrame` onto the target's portrait, repositions `ComboPoint1..8` and re-registers its events, but only calls `ComboFrame:Hide()` on the `comboPoints == 0` branch — a branch that a class without combo points (shaman, priest, …) never reaches, so its five empty slots sit on the unit frame forever as a row of black dots. Guard the whole combo-block: `UnitPowerMax("player", Enum.PowerType.ComboPoints) <= 0` → hide it through the keep-hidden helper (Show hook + post-combat retry, since Blizzard re-shows it on target changes) and return; treat an unreadable (secret) max as "do not hide" so rogues/druids in restricted windows keep their display.
- Cheap triage before blaming code: check `WTF/Config.wtf` for forced secret simulation (`addonMapRestrictionsForced`, `addonCombatRestrictionsForced`, `addonEncounterRestrictionsForced`, `addonChallengeModeRestrictionsForced`, `addonPvPMatchRestrictionsForced`) — any of these set makes restricted-context behaviour happen everywhere.
- Spell-cast paths (cast bar event handlers) receive secret strings AND numbers: `SetFont/SetText(secret)` is fine, but any indexing, strfind, gsub or comparison on `name`/`text` errors, and arithmetic on secret `startTime`/`endTime` errors too. Guard every `UnitCastingInfo`/`UnitChannelInfo` call site. PITFALL: guarding only the use site is not enough — handlers like DELAYED/CHANNEL_UPDATE store `startTime`/`endTime` into frame fields that a later OnUpdate does arithmetic on (`self.endTime - GetTime()`), so the stored value must be clean: `if issecretvalue(startTime) or issecretvalue(endTime) then return end` BEFORE storing (keep the bar frozen rather than storing a secret). Helper predicates that re-read the cast info (`ActiveCasting`-style `endTime > GetTime()+500` checks) need the same guard.
- "Target/unit shows dead/offline/ghost while alive" is the status-text variant of the one-cause rule, and the APIs behind it are NOT in the headline secret lists: `UnitIsDead`/`UnitIsGhost`/`UnitIsConnected` carry the `AllowedWhenUntainted` predicate — check the wiki API page's **Predicates** line; any predicate listed means the API can return secrets (or nil) in restricted windows. Two-part fix: (1) when the health read itself is secret (`hp, hpMax, isSecret = SafeHealth(unit)`), skip the ENTIRE dead/ghost/offline/AFK status-text branch AND the grey-out — feed the bar and return; a wrong label is worse than no label, and the frame's own status logic must not run on unreliable booleans. (2) offline tests must be strict: `UnitIsConnected(unit) == false` (only a definite false is offline), never `not UnitIsConnected(unit)` — `not` turns a safe-wrapper fallback *or a raw nil* into "offline". Do NOT fix this by making the SafeBool wrapper swallow nil globally: `UnitExists` legitimately returns nil for "no unit" and frame-hiding logic depends on that nil being real; keep nil semantics in the wrapper and make the status-text call site strict instead.
- **One frame of a family sitting at the template's RAW XML geometry means the layout function never ran on it — that is not a wrong-layout bug.** Tell them apart by size: the fat/proportional branch of Z-Perl's `QueFrame_StatsFrameSetup` produces e.g. 115px wide bars, the non-fat branch 109px, and the untouched template exactly `112x10` (its single TOPLEFT anchor and `<Size>`). A 112x10 bar in a 160x40 box, 9px of dead space above and below, is "never laid out". Root cause seen live: the statsFrame template's own OnLoad calls `QueFrame_StatsFrame_Setup(self)` with the **statsFrame** as the argument while the function's first real line is `local StatsFrame = self.statsFrame` (i.e. it wants the UNIT frame) — so that call returns immediately and is dead for every frame that inherits the template. Frames survive it because their module re-lays-out on every update (the player frame re-runs it from its health/mana/druid update paths); the target frame does not — its only other call sites are conditional (mana-bar show/hide transitions inside `SetManaType`, and the options pass), none of which fire in a normal session. Fix in the shared function, not per module: resolve `self` when it is a statsFrame (`self:GetName() == parent:GetName().."statsFrame"`, or `parent.statsFrame == self` when already wired), fall back to the parent, and retry once via `C_Timer` when the config is not readable yet — that restores the template OnLoad for every frame at once and needs no XML edit.
- **Before assuming a module re-lays-out its bars, count its `StatsFrameSetup` call sites and their conditions.** "Runs on every update" (player, targettarget) and "only when a bar's shown-state changes / the options pane is touched" (target) look identical in the code and behave completely differently: the second frame keeps its template geometry for the whole session. Same shape applies to the resource-bar type change path.

## Taint from embedding or re-parenting Blizzard frames (12.x)

- Owning a Blizzard-templated frame from addon code — `CreateFrame(..., "MonkHarmonyBarFrameTemplate")` or `SetParent(ours)` on an existing one — makes that frame's own update handlers (`OnShow`/`OnEvent`/`OnUpdate`) run **inside your tainted execution**; if it holds secret values (class power/stagger/essence/rune bars, eclipse bar, …) its own comparisons then error in a stack that points at a Blizzard file, e.g. `Blizzard_TextStatusBar/TextStatusBar.lua:344: attempt to compare local 'minValue' (a secret number value, while execution tainted by 'ZPerl_Player')`. The `tainted by 'X'` clause names the addon that owns the frame — that is where the fix goes, not in the Blizzard file the stack points at.
- Even a *redundant* `SetParent` call — reparenting to the parent the frame already has — fires that handler. Guard it: `if frame:GetParent() ~= parent then pcall(frame.SetParent, frame, parent) end` (wrap the `GetParent` compare in pcall too; it can return a secret).
- For Blizzard class-power templates **created** from addon code, the SetParent guard is not enough — the taint source is the CreateFrame embed itself, and the template's value updates keep erroring every frame after it loads. The only clean fix on 12.x is to not create the template at all: define one TOC-gated flag in the compat shim (`XPerl_SecretTemplatesBroken = math.floor(select(4, GetBuildInfo()) / 10000) >= 120000`) and gate the whole family of init calls at the dispatcher call site, not per-function — all class-power inits share the same embed pattern, and fixing only the class that first errored (the user's class) leaves the other eight to fire later. State the trade-off: those energy bars disappear from the unit frames; only a purpose-built reimplementation brings them back.
- `pcall` does not rescue these errors: they fire inside Blizzard's own handler after the protected call returns, and protected operations (`SetParent` on unit frames, CLEU registration) additionally raise `ADDON_ACTION_FORBIDDEN` warnings that pcall cannot suppress.
- Do not "fix" it by anchoring the Blizzard frame to your frame instead: a frame holding secrets propagates secret anchoring to everything anchored to it, which poisons your own layout maths.
- **Suppressing Blizzard's own unit frames needs more than one `Hide()`.** `frame:Hide()` + `SetParent(hiddenParent)` is undone the next time Blizzard shows the frame (roster change, group-type switch, entering a vehicle), and a PROTECTED frame cannot be hidden at all while in combat — the call silently does nothing, so an in-combat re-show leaves Blizzard's frame on screen permanently. Keep it down with `frame:HookScript("OnShow", function(f) f:Hide() ... end)` plus a post-combat retry: queue the frame and re-hide it on `PLAYER_REGEN_ENABLED`. Two traps: set the "already handled" flag BEFORE calling the disable helper the hook delegates to (else helper and hook recurse into each other), and keep the disable helper itself alive for the modules that call it later (see the rename section's `= nil` bullet).

## Aura frames after 12.1 (SecureAuraHeaderTemplate removal)

- 12.1 removed `SecureAuraHeaderTemplate` from mainline (`CreateFrame` errors with `Couldn't find inherited node`). Migration = `AuraContainer`/`AuraButton` intrinsic frames; `SecureGroupHeaderTemplate` still exists for Classic.
- Working shape (verified against `BetterBlizzFrames/retail/modules/auras.lua`, which is the local reference to read first — also Grid2):
  `local c = CreateFrame("AuraContainer", nil, parent, "CustomAuraContainerTemplate")` → `c:SetSize(1,1)` → `c:SetUnit(unit)` → optional `SetFlowLayoutAxis(AnchorUtil.FlowLayoutAxis.Horizontal)/SetFlowLayoutAnchorPoint("TOPLEFT")/SetFlowLayoutGrowthDirection(AnchorUtil.FlowDirection.Right, AnchorUtil.FlowDirection.Down)/SetFlowLayoutPadding(0,0,0,0)` → `c:AddAuraGroup(key, "HELPFUL"|"HARMFUL", { maxFrameCount = n, initializeFrame = function(button) … end })`.
  Per button: `CreateTexture` + `button:SetIcon(tex)`; `CreateFontString` + `button:SetDurationText(fs)`; `CreateFontString` + `button:SetApplicationCount(fs)`; `CreateFrame("Cooldown", nil, button, "CooldownFrameTemplate")` + `button:SetDurationCooldown(cd)`; `button:SetCancelAuraButtons("RightButtonUp")`; `button:SetHideTooltipInCombat(bool)`.
- Wrap the container build in `pcall` and keep the old secure-header path as the fallback for non-retail clients; on mainline a failed build should silently skip the display rather than error every login. Groups cannot be created in combat on 12.1.0 (defer like the old header code did).

- AuraContainer/AuraButton are **forbidden frames** for the SecureHandlers API in 12.1: `state:SetFrameRef("X", container)` errors with `Cannot use SecureHandlers API on forbidden frames` (Blizzard_RestrictedAddOnEnvironment/SecureHandlers.lua). When you port a secure aura header to a container, create a plain `Frame` anchor, hand *that* to the secure state driver, anchor the containers to the anchor, and make the insecure positioning code move the anchor (`local buffFrame = self.buffAnchor or self.buffFrame` at the top of the position function, plus skip the old header-only arrangement call). The secure snippet keeps working and never touches the container. Wrap the SetFrameRef in `pcall` too.
- Wrapping the API *captures* (`local UnitIsAFK = XPerl_SafeBoolAPI(UnitIsAFK, "UnitIsAFK")`) is the cheapest way to make a whole file secret-safe: one edit per API per file, the game's globals stay untouched so other addons are unaffected. Per-API fallback matters — `UnitIsAFK/DND/Dead/Charmed/PVP/GroupLeader` → false, but `UnitExists/UnitIsConnected/UnitIsVisible/UnitInParty/UnitInRaid/UnitIsFriend` → **true**, otherwise party frames get marked offline or stop updating. `UnitIsUnit` → true where it gates an event handler ("is this event for my frame"), false where it is real logic. Re-capture locals in the shim itself for helpers that use the raw API internally (a `UnitIsGhost(unit) and 1 or ...` inside your own helper errors too), and never capture inside `.toc`-loaded Libs. **Wrapping the header captures is mandatory, not cosmetic, for every unit module**: the ubiquitous health idiom `UnitIsGhost(unit) and 1 or (UnitIsDead(unit) and 0 or UnitHealth(unit))` is a boolean test on a possibly-secret boolean, which is a forbidden operation, so an unwrapped module throws on its first health update. Copy the whole capture list from an already-patched SIBLING module of the same addon (same APIs, same helper names, same fallback directions) instead of deriving it API by API — the patched sibling has already had the per-API fallback directions worked out — they load before your shim, so the wrapper name is still nil and the lib fails to load.
- Class colours / class icons after 12.1: `UnitIsPlayer` comes back as a secret boolean and `UnitClass` as a secret string in restricted windows (which include dungeons/raid for **party members and the player**, not just enemies), so both the "is this a player" gate and the class lookup need the safe path. PITFALL: wrapping the API capture with a swallowing fallback (`local UnitIsPlayer = XPerl_SafeBoolAPI(...)`) makes the fallback return **false** before any outer `XPerl_SafeBool(UnitIsPlayer(unit), fallback)` ever runs — the outer fallback is dead code and the colour branch silently never fires (no error, just missing colours). When a call site needs "unreadable" distinguished from a real `false`, expose a raw passthrough that returns a sentinel string on secrets (`XPerl_RawBoolAPI(fn)` → `XPerl_SECRET_SENTINEL`) and test `raw == true or (raw == SENTINEL and classToken ~= nil)`. Cache the class token per unit together with the unit's GUID and only reuse it when the GUID is verifiably unchanged or the token cannot change identity (`player`/`party*`/`raid*`/`pet`/`vehicle`) — otherwise a target switch plus a restricted window paints the new target with the previous one's colour. Remember the player's own class separately so the player frame stays coloured inside instances. `UnitClass` returns `localisedName, token` — take `select(2, ...)`. `UnitClassBase` also returns secrets; guard with a pcall'd `XPerl_SafeValue` and fall back to the cached token.
- Two-tier class-token reads: a *strict* reader (returns nil when the read is secret/unreadable) for identity gates — portraits, class icons, "is this a player" decisions where a stale class misleads; and a *lenient cached* reader for cosmetics (health-bar colour, name colour) that returns the last known class when the strict read fails, so the colour survives the whole restricted window instead of dropping to default mid-combat. The lenient cache must record the GUID alongside the class and drop the entry when a readable GUID differs (target switched from player A to B) — otherwise A's colour bleeds onto B. In the window where neither class nor GUID is readable (the platform limit), a stale colour stands until the next readable read corrects it. Route colour-bar/name-colour call sites through the lenient variant; keep identity-sensitive decisions on the strict one.
## Full addon rename (rebranding a ported addon)

- Ask scope BEFORE touching files: (1) external-only (dirs, TOC, slash, SavedVariables, texture paths) vs ALSO the internal code prefixes (`XPerl_` → `QueFrame_`, `XPERL_` → `QUEFRAME_` — thousands of sites across 50+ files); (2) SavedVariables rename resets the user's config — confirm that is acceptable; (3) the new slash commands. A "change everything" user picks the full rename and accepts the config reset.
- Rename on a COPY first: duplicate all module dirs, run replacement + file/dir rename on the copy, run the full verification there, then delete the old dirs and deploy. Never rename in place on the live tree; keep a pre-rename backup for rollback.
- Replacement order is the whole game — run ordered `str.replace` passes, most-specific token first so shorter tokens never eat longer ones: `XPerl_` → new prefix, `XPERL_` → new constant prefix, `XPerlDB` → new config object, then the SavedVariables family longest-first (`ZPerlConfigSavePerCharacter` → `ZPerlConfig_Global` → `ZPerlConfigNew` → `ZPerlConfig` → `ZPerlImportDone`), then `ZPerlVersion` (chat channel), `ZPERL_` (bindings), then `ZPerl` → new name LAST, then the slash commands (`/zperl` → `/que`, `/zp` → `/qframe`). Reverse order corrupts tokens — a short `ZPerl` pass first mangles every `ZPerlConfig*` into a double-renamed mess.
- Rename files (`ZPerl*.lua/xml/toc/blp` → `QueFrame*...`) and top-level dirs after the content pass, via Python `os.rename`.
- Deliberately preserve (blanket replace breaks them): option/config-key names that embed the old name (`XPERLOLDROLEICONS` is an option key — renaming it orphans the saved option), legacy-config migration detectors (`strfind(str, "^XPERL")` reads old keys), and keep `SlashCmdList["NewName"]` in lockstep with `SLASH_NewName1/2` or the command silently dies.
- **A blanket rename ACTIVATES dead upstream references.** Upstream X-Perl forks are full of hardcoded pre-fork name strings that were inert because that addon did not exist (`C_AddOns.DisableAddOn("XPerl")`, `C_AddOns.IsAddOnLoaded("XPerl")`, `EnableAddOn("XPerl")` inside the ADDON_LOADED handler). Renamed to the live name they become real self-calls. `DisableAddOn(<own name>)` inside the ADDON_LOADED handler self-disables the addon on EVERY login: the client then also refuses `LoadAddOn` on that addon's modules, so a LoadOnDemand module (Options) never loads, `*_Defaults` falls back to a partial table, unit sections stay nil, and on logout the game writes `<Name>: disabled` into AddOns.txt — so after the restart the addon does not load at all and the user reports "无法加载". Before renaming, grep the PRISTINE source for the old name as a bare string literal and decide per site; never let the addon call Disable/EnableAddOn on itself from its own load path. Symptom triad to recognise: AddOns.txt says disabled + module LoadOptions returns false + saved config contains only the fallback subset.
- **A rename also exposes globals the core DELETES during init while later-loading modules still call them.** Ported cores clean up their namespace at the end of their own init handler (`XPerl_BlizzFrameDisable = nil` living alongside the other `= nil` lines), but module addons' ADDON_LOADED handlers fire AFTER the core's, so any module that calls such a helper throws `attempt to call a nil value` and aborts its ENTIRE init — unit frames half-built, Blizzard's frames never disabled, and the only symptom is a feature that silently does nothing. Sweep it mechanically: list every `^\s*(\w+)\s*=\s*nil` in the globals/init file and grep the module files for `\bName\s*\(`; keep the used ones alive (comment the `= nil` out) and nil-guard the call sites.
- **A rename can also turn a registry TABLE into a function without anyone noticing.** After prefix renames, sweep for `\b<FunctionName>\s*\[` over every name the tree defines as `^\s*function\s+<Name>\s*\(`: a leftover `Name[frame] = true` / `if (Name[frame]) then` then throws `attempt to index global 'Name' (a function value)` and **aborts the rest of the function** — live case: `QueFrame_KeepBlizzFrameHidden[frame]` inside the helper of the same name, BugGrabber counter 10, and the abort happened before the OnShow hook was installed, so Blizzard's party frames were never re-hidden. Keep the registry in its own local table; the sweep (defined-function names used as tables) is one regex pass over the tree and found exactly that one site.
- Verify the rename against the pristine tree by AUDITING, not by eye: TOC/XML `file=` refs, `## Interface`, module `RequiredDeps`/`LoadOnDemand`, and TOC line endings (BOM/mixed CRLF are worth ruling out). If all of those are clean, the failure is behavioural (see the self-disable bullet), not structural — stop diffing files and read the ADDON_LOADED handler.
- The `## Version:` string is load-bearing, not just a display value: it is compared against the saved `ConfigVersion` to decide whether the addon runs its own `UpgradeSettings` migration pass, and that pass compares versions as PLAIN STRINGS (`oldVersion < "7.0.7"`), so a scheme the user picks for looks (`12.1`) sorts BELOW the legacy numbers. Before changing it, enumerate every comparison in the migration function and work out which ones fire for the currently saved version (all-false ⇒ one harmless pass); update the metadata fallbacks in lockstep (`C_AddOns.GetAddOnMetadata(name, "Version") or "<old>"` sits in 2-3 files and resurrects the old number if that read ever fails). Never touch `## Interface:` while doing it — that is the client's load gate (12.1.0 = `120100`), not a display string.
- After the rename, do a second TOC-scoped pass: `## Title`/`## Notes` display names still carry the old hyphenated brand (`Z-Perl` survives a `ZPerl` replace) — regex `## (Title|Notes)[^\n]*OldBrand` → new name across ALL languages, and update `## Author:`.
- Verification checklist (run on the copy before deploy): residual grep `\bOldName\w*\b|\bOldPrefix\w*\b` over .lua/.xml/.toc — expect only the deliberate residuals; every `file="..."` ref in XML and every TOC entry resolves to an existing file; every `Interface\AddOns\<Name>\` texture path starts with the new dir; `C_AddOns.GetAddOnMetadata("NewName", ...)` self-refs updated; luaparser every .lua + ElementTree every .xml. `C_AddOns.IsAddOnLoaded("OldName_Module")` checks for modules the user does not have installed are harmless dead branches.
### Adding more upstream modules to an already-renamed install (the user drops new dirs into AddOns)

- Read the rename mapping OFF the installed core's TOC instead of reconstructing it: `## SavedVariables:`, `## RequiredDeps`, `## Interface:`, `## Author:` and the `SLASH_*` names in 2-3 of the live TOCs are the authoritative target tokens (`SavedVariables: QueFrameConfig, QueFrameConfig_Global, QueFrameConfigNew, QueFrameConfigSavePerCharacter, QueFrameImportDone`). Guessing these produces an install whose config silently never loads.
- Stock TOCs carry a multi-value interface line (`## Interface: 11508, 20505, 50504`) that no content replacement fixes — collapse it with a TOC-specific regex pass (`^## Interface:.*$` → single current value) plus `^## Author:.*$`, in the same run as the rename.
- **Pick the source per module: prefer an already-PATCHED local reference tree over the user's fresh stock copies.** Diff one representative file per module against the patched tree; a difference in `SafeBoolAPI` / `IsSecretValue` counts means the user's copy is stock and will need the entire 12.x pass, while the patched copy carries it already. Taking the patched copy for the modules that have one saves a whole fix pass (it did for 3 of 8) — and do not trust your own "source used" bookkeeping label, assert it from the copied file's content.
- The user copies the whole upstream set, so some dirs duplicate modules already installed under the new name — detect the collision on the mapped name and SKIP it (report the skip) rather than writing a second tree with the same addon name.
- After copy+rename, MOVE the stock `Old*` dirs out of `Interface/AddOns` into a dated backup (move, never delete) — two trees with the same frames both load and the user sees doubled unit frames.
- Verification that actually catches module-copy mistakes: luaparser over every .lua + ElementTree over every .xml; every TOC line resolving to an existing file; every XML `file="..."` that begins `Interface\AddOns\<Module>\` resolving after stripping that prefix. Do NOT feed engine asset paths (`Interface\TargetingFrame\UI-StatusBar`, `Interface\Buttons\White8x8`, `Interface\Minimap\Ping\ping6`) into the addon-file existence check — they are Blizzard assets and a naive check reports 150+ phantom misses that bury the real ones.
- **Scope the AddOns.txt edit to the character the user actually plays.** Every character of every account has its own `AddOns.txt`; enabling the addon family across all of them is an unrequested, surprising change. Identify the active account/character (saved-variables mtime, the character the user names) and edit only that file; mention the others as available rather than flipping them.
- Newly copied modules must be `enabled` in that AddOns.txt or they never load — add missing entries and flip `disabled` to `enabled` there, and remember the client reads this file at startup, so a running client needs a reload to notice.
- **A newly installed or renamed addon directory is only picked up when the CLIENT starts — `/reload` does not rescan `Interface/AddOns`.** Have the user exit to character select and re-enter (a full restart is not needed) after a batch of new dirs is dropped in. The trap: until then the module produces no errors at all, which reads exactly like "loaded clean". Prove loading POSITIVELY with the module's own per-character SavedVariables file (`WTF/Account/<acct>/<realm>/<char>/SavedVariables/<Module>_*.lua`, from its `SavedVariablesPerCharacter` TOC line) or the core's probe keys changing — an empty BugGrabber plus a stale save is the signature of "never ran", not of success.
- **"改成玩家和目标的样子" / "make it work like the player and target frames" means FUNCTIONAL parity, not restyling.** Route the new module through the SAME shared helpers (the bar setter plus the class-colour and text helpers) so it inherits class colour, exact numbers and percent for free, and get it LOADING and error-free first. Ask about size/portrait/font/position as a separate question — inferring a visual clone from the wording leads to editing per-frame config when the user wanted the module to stop being broken.
- Order of work: rename + TOC + static verify, then wire the unit-frame modules to the shared bar/text helpers, then have the user reload and read BugGrabber + the alias probe BEFORE investing in the utility panels (raid helper/admin/monitor style modules). The reload names which remaining aliases are actually nil and which module errors first — fixing a 40-file utility batch blind is wasted work.
- Re-run the alias sweep after adding modules and extend the login probe's name list with the new files' aliases (`^local (\w+) = \1$`), so one reload reports the new modules' removed APIs too.

## Windows tooling notes

- Pass `C:/<path>/...` forward-slash NATIVE paths to native tools (git, python, node); MSYS-shaped `/c/Users/...` arguments are not translated and fail with 'cannot change to' / 'No such file or directory' even though `cd /c/Users/...` (a bash builtin) works.
- `python -c "..."` / heredoc Python carrying backslashes in regexes dies with "unterminated string literal" — write a .py with write_file and run it.
- A whole-tree luaparser walk can time out the execute_code kernel — run it per-directory with a timeout from terminal.

## Procedure

1. Identify the installed addon and version - scan `Interface/AddOns/`, grep each TOC for `## Interface:` / `## Version:`. Diff against the canonical GitHub/CurseForge source to confirm it is stock (line-ending-only diffs are noise).
2. Pull the API-change baseline - `warcraft.wiki.gg/wiki/Patch_12.0.0/API_changes` and `.../Patch_12.1.0/API_changes` (web_extract). Key 12.x facts - forced interface matching; Secret Values on combat data (arithmetic/comparison on combat-time `UnitHealth`/`UnitPower` results can error); `COMBAT_LOG_EVENT(_UNFILTERED)` errors on RegisterEvent; global spell/item/container APIs moved to `C_Spell` / `C_Item` / `C_Container` namespaces; `getglobal`/`setglobal` and `UIParentLoadAddOn` removed.
3. Inventory what the addon actually uses. Grep non-Libs code for - `GetSpellInfo`, `GetSpellTexture/Link/Cooldown/Charges`, `IsSpellInRange`, `UnitAura/UnitBuff/UnitDebuff`, `GetItemInfo/GetItemCount/GetContainer*`, `GetTalentInfo/GetNumTalents/GetActiveSpecGroup`, `RegisterEvent("COMBAT_LOG`, `getglobal`. Use python (execute_code) with a word-boundary regex per API and a per-file hit list — the codebase is too big for manual greps.
4. Check which risky call sites are already guarded - much 11.x-era code branches `if C_UnitAuras then ... else UnitAura(...)`. The `else` branches may be dead on retail — fix only sites that actually execute, plus add the shim for the rest.
5. Write one `Addon_Compat.lua` shim (signatures in `references/12x-api-replacements.md`) and insert it at the top of the main TOC.
6. Fix load-time (top-level, inside `if IsRetail` tables) unguarded lookups - `[C_Spell.GetSpellInfo(N).name] = ...` dies if that spell ID was removed this expansion. Convert to `[(C_Spell.GetSpellInfo(N) and C_Spell.GetSpellInfo(N).name)] = ...`. Distinguish load-time table-building code from runtime function bodies — only the former must be guarded by hand; runtime sites are covered by the shim.
7. Wrap `RegisterEvent("COMBAT_LOG_EVENT_UNFILTERED")` in `if not pcall(self.RegisterEvent, self, "...") then self:UnregisterEvent(...) end`. Leave occurrences inside `--[[ ]]` blocks alone. Libs often early-return on non-classic (`if WOW_PROJECT_ID ~= WOW_PROJECT_CLASSIC then return end`), so their CLEU registrations are dormant on retail — check before touching them.
8. Verify offline - `pip install luaparser` and AST-parse every touched/related .lua (also gives a pre-existing-error baseline for untouched files); parse all .xml with ElementTree for well-formedness. Then hand the user the in-game test checklist.
9. Triage live errors. Preferred source is BugGrabber's SavedVariables — read `WTF/Account/<account>/SavedVariables/!BugGrabber.lua` directly from disk: each entry has `"message"`, `"stack"`, and `"counter"` (frequency), parseable with a regex over Lua-string escapes. The `locals` block in each entry is a free bug-localizer: it shows the caller frame's unit (`unit="target"`) and which arguments were already secret at the error site (`name=<secret string>`), which pinpoints the guard placement without re-deriving it from the stack. If the user hand-transfers errors into a .txt, verify the file is non-empty before trusting it — failed save-as produces 0-byte files that look like a successful transfer. `/bugsack` paste-back or a screenshot works too. `[string "*File.xml:LINE_OnUpdate"]:N: attempt to call a nil value` means a REMOVED global called inside an XML script block — grep the .xml files for removed-API names too (step 3 usually only scans .lua). Prefer replacing with the frame method (`MouseIsOver(self)` → `self:IsMouseOver()`) — object methods survive global removal. Errors from OnUpdate repeat every frame (counter in the hundreds), so fix them first; the count is diagnostic, not severity.
10. Iterate: one BugSack paste per round, fix all distinct nil-call sites found (shim or method swap), re-verify syntax, hand back. Expect 2-3 rounds for a 55k-line addon.

- Aura-scanning hot paths (`C_UnitAuras.GetAuraDataByIndex`) survive a restricted context only through a guarded accessor: `pcall` the call and reject `issecrettable(result)`, returning nil so the caller sees "no aura". Route every call site through it — the loop then breaks after one probe instead of erroring. The linter still reports the accessor's own body; that one is expected.
- Patch by line index, not by long exact strings: build the edit list, sort it **descending by line number**, assert a distinctive anchor is present in the target range, then write once. Afterwards diff the patched file against the pristine repo copy and review every hunk — an off-by-N index silently deletes a function header and the damage only shows up as a parse error hundreds of lines later. `luaparser` for Lua and `ElementTree` for XML are the last gate; hand the user the in-game checklist (`/console scriptErrors 1`, BugSack paste) after that.

For the verified 12.x removed-API → replacement mapping, see `references/12x-api-replacements.md`.
For pulling hard measurements out of a live client you cannot drive yourself — session/reload timing, SavedVariables probes, pixel and log evidence — see `references/live-client-measurement.md`.

## Known 12.x behavior changes to warn the user about (not fixable addon-side)

- The installed AddOns tree for a long-running port is an ACCUMULATED patched build, not stock (its TOC interface/version won't match the upstream repo's latest). Keep a backup copy of the patched tree (e.g. `<home>\ZPerl-12.1-patched`) and refresh it after every accepted fix round, so a bad edit round can be rolled back file-by-file.
- Check the upstream repo before writing secret handling yourself: if the author has since shipped a real 12.x-compatible version, the whole hand-written compat layer may be obsolete — port onto theirs. If they have not (Z-Perl's retail TOC still targets classic interface numbers), the local patched build is the only retail-compatible variant and the compat layer must be maintained locally.

- Combat-log-driven features (HoT/shield highlight via CLEU) degrade because the event is gone for addons — registration is silenced, the handler just never fires.
- Combat-time health/power values are Secret Values - display works, arithmetic may error. If the user reports "secret value" errors in combat, that needs per-site rework (compare-guard, or Blizzard's unit percent APIs), not the shim.
